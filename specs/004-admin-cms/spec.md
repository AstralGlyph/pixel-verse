# Feature Specification: 后台内容管理系统 (Admin CMS)

**Feature Branch**: `004-admin-cms`  
**Created**: 2026-04-01  
**Status**: Draft  
**Input**: User description: 我需要有个后台可以管理所有的内容和数据信息，而不是通过git的方式进行管理

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员登录与仪表盘访问 (Priority: P1)

作为系统管理员，我需要登录后台管理系统，进入一个可视化的仪表盘界面，以便快速了解系统的整体状态和内容概况。

**Why this priority**: 登录和仪表盘是后台管理系统的入口，是所有后续操作的前提条件。没有认证机制，系统无法安全使用。

**Independent Test**: 可以通过输入正确的管理员凭据登录系统，并成功访问仪表盘页面，看到内容统计概览。

**Acceptance Scenarios**:

1. **Given** 管理员拥有有效的账号和密码，**When** 在登录页面输入凭据并提交，**Then** 系统验证通过并跳转至仪表盘页面
2. **Given** 管理员输入了错误的密码，**When** 提交登录表单，**Then** 系统显示明确的错误提示且拒绝访问
3. **Given** 管理员已登录，**When** 访问仪表盘页面，**Then** 系统展示内容数量统计、最近操作记录等概览信息

---

### User Story 2 - 博客文章的创建、编辑与发布 (Priority: P1)

作为内容编辑者，我需要通过后台界面创建、编辑和发布博客文章，以便在不使用 Git 的情况下管理网站内容。

**Why this priority**: 博客文章是网站的核心内容，能够直接通过后台管理文章是整个 CMS 最重要的功能。

**Independent Test**: 可以通过后台创建一篇新文章、编辑已有文章、预览文章内容，并将其发布到网站上，整个过程无需任何 Git 操作。

**Acceptance Scenarios**:

1. **Given** 管理员在文章列表页面，**When** 点击"新建文章"按钮，**Then** 系统打开文章编辑器界面
2. **Given** 管理员在编辑器中填写了标题和内容，**When** 点击"保存草稿"，**Then** 文章以草稿状态保存，可在文章列表中查看
3. **Given** 管理员编辑了一篇草稿文章，**When** 点击"发布"，**Then** 文章状态变为已发布，并立即在前台网站可见
4. **Given** 管理员在文章列表中选中一篇文章，**When** 点击"编辑"，**Then** 系统加载该文章的完整内容到编辑器中
5. **Given** 管理员在编辑器中修改了文章内容，**When** 点击"预览"，**Then** 系统展示文章在前台的渲染效果

---

### User Story 3 - 内容分类与标签管理 (Priority: P2)

作为内容编辑者，我需要管理文章的分类和标签，以便对内容进行组织并帮助用户快速找到感兴趣的内容。

**Why this priority**: 分类和标签是内容组织的基础设施，影响用户体验和内容的可发现性。

**Independent Test**: 可以创建、编辑和删除分类及标签，并在编辑文章时为其分配分类和标签。

**Acceptance Scenarios**:

1. **Given** 管理员在分类管理页面，**When** 创建新分类并填写名称和描述，**Then** 分类被保存并显示在分类列表中
2. **Given** 管理员在编辑文章时，**When** 为文章选择分类和添加标签，**Then** 保存后文章与所选分类和标签关联
3. **Given** 管理员尝试删除一个已有文章使用的分类，**When** 确认删除操作，**Then** 系统提示该分类下有文章并询问如何处理（转移或一并删除）

---

### User Story 4 - 媒体文件管理 (Priority: P2)

作为内容编辑者，我需要上传、浏览和管理媒体文件（图片、视频、文档等），以便在文章中插入多媒体内容。

**Why this priority**: 富文本内容需要媒体文件支持，媒体库是内容编辑的基础设施。

**Independent Test**: 可以上传文件到媒体库、浏览已有文件、删除不需要的文件，并在文章编辑器中插入媒体文件。

**Acceptance Scenarios**:

1. **Given** 管理员在媒体库页面，**When** 拖拽或选择文件上传，**Then** 文件上传成功并显示在媒体库中
2. **Given** 管理员在文章编辑器中，**When** 点击"插入图片"并选择媒体库中的文件，**Then** 图片被插入到文章的光标位置
3. **Given** 管理员尝试上传超过大小限制的文件，**When** 选择文件后，**Then** 系统提示文件大小超出限制并拒绝上传

---

### User Story 5 - 页面管理 (Priority: P3)

作为站点管理员，我需要创建和管理静态页面（如关于页面、联系页面等），以便维护网站的非博客内容。

**Why this priority**: 静态页面是网站的重要组成部分，但相对于博客文章使用频率较低。

**Independent Test**: 可以创建新的静态页面、编辑页面内容、发布和下线页面。

**Acceptance Scenarios**:

1. **Given** 管理员在页面管理列表，**When** 创建新页面并填写标题和内容，**Then** 页面被保存并可在前台访问
2. **Given** 管理员需要下线一个已发布的页面，**When** 将页面状态改为草稿，**Then** 页面从前台移除但仍保留在后台

---

### User Story 6 - 用户与权限管理 (Priority: P3)

作为超级管理员，我需要管理后台用户及其权限角色，以便控制不同人员对内容的操作权限。

**Why this priority**: 多用户协作是后台系统的扩展需求，初期单人使用可以不依赖此功能，但架构上需要预留。

**Independent Test**: 可以创建新用户、分配角色（管理员、编辑者、作者），并验证不同角色的权限边界。

**Acceptance Scenarios**:

1. **Given** 超级管理员在用户管理页面，**When** 创建新用户并分配"编辑者"角色，**Then** 该用户可以登录后台并拥有编辑者权限
2. **Given** 一个"作者"角色的用户尝试删除他人文章，**When** 执行删除操作，**Then** 系统拒绝操作并提示权限不足

---

### Edge Cases

- 当网络中断时，正在编辑的文章内容是否自动保存？系统应提供本地草稿自动保存机制，网络恢复后自动同步
- 当多个编辑者同时编辑同一篇文章时如何处理？系统应提供锁定机制或冲突提示
- 当删除一个被多篇文章引用的标签时，系统应提示影响范围并确认操作
- 当上传的文件格式不支持时，系统应明确提示支持的文件格式列表
- 当发布文章时必填字段（如标题）为空时，系统应阻止发布并高亮提示

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供管理员身份认证机制，支持用户名和密码登录
- **FR-002**: 系统 MUST 提供可视化仪表盘，展示内容统计概览（文章数量、分类数量、最近操作等）
- **FR-003**: 系统 MUST 支持创建、编辑、保存草稿、发布、更新和删除博客文章
- **FR-004**: 系统 MUST 提供富文本编辑器，支持标题、段落、列表、引用、代码块、图片插入等常见格式
- **FR-005**: 系统 MUST 支持文章的分类和标签管理，包括创建、编辑、删除和关联操作
- **FR-006**: 系统 MUST 提供媒体库功能，支持文件上传、浏览、搜索和删除
- **FR-007**: 系统 MUST 支持在文章编辑器中插入媒体库中的文件
- **FR-008**: 系统 MUST 支持静态页面的创建、编辑、发布和下线管理
- **FR-009**: 系统 MUST 支持文章列表的多条件筛选（按状态、分类、标签、作者、日期范围）
- **FR-010**: 系统 MUST 支持文章内容的自动保存（本地草稿机制），防止编辑过程中数据丢失
- **FR-011**: 系统 MUST 提供用户与角色管理机制，支持至少三种角色：超级管理员、编辑者、作者
- **FR-012**: 系统 MUST 记录关键操作日志（发布、删除、用户变更等），包含操作人、操作时间和操作内容
- **FR-013**: 系统 MUST 支持文章 URL 别名（slug）的自定义和自动生成
- **FR-014**: 系统 MUST 支持文章的 SEO 元数据编辑（标题、描述、关键词）
- **FR-015**: 系统 MUST 提供响应式后台界面，支持桌面端和移动端访问
- **FR-016**: 系统 MUST 在内容发布后实时更新前台网站展示，无需手动构建或部署（采用 SSR 模式，Astro 从数据库实时读取内容）

### Key Entities

- **文章 (Article/Post)**: 代表一篇博客文章，包含标题、内容（富文本）、URL 别名、状态（草稿/已发布/已归档）、作者、分类、标签、SEO 元数据、创建时间和更新时间
- **分类 (Category)**: 文章的分类标签，包含名称、描述、URL 别名，与文章为一对多关系
- **标签 (Tag)**: 文章的自由标签，包含名称和 URL 别名，与文章为多对多关系
- **媒体文件 (Media)**: 上传的文件资源，包含文件名、文件类型、文件大小、存储路径、上传者和上传时间
- **页面 (Page)**: 静态页面，包含标题、内容（富文本）、URL 别名、状态和创建时间
- **用户 (User)**: 后台系统用户，包含用户名、密码（加密存储）、角色、邮箱和创建时间
- **角色 (Role)**: 权限角色定义，包含角色名称和权限列表
- **操作日志 (AuditLog)**: 操作记录，包含操作人、操作类型、目标对象、操作时间和操作详情

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员可以在 5 分钟内完成一篇博客文章的创建、编辑和发布全流程
- **SC-002**: 内容编辑者可以在不接触 Git 或命令行工具的情况下，独立完成所有内容管理操作
- **SC-003**: 文章发布后，前台网站在 30 秒内展示最新内容
- **SC-004**: 系统支持同时管理 1000 篇以上的文章而不出现性能退化
- **SC-005**: 95% 的内容编辑操作（创建、编辑、发布）可以在首次使用的用户无需培训的情况下完成
- **SC-006**: 编辑过程中的自动保存机制确保数据丢失风险降低至零（即用户不会因意外关闭浏览器而丢失编辑内容）

## Assumptions

- 目标用户为具备基本计算机操作能力的内容编辑者，不需要技术背景
- 后台管理系统将作为现有 Astro 博客站点的补充，不替代前台展示功能
- 初期支持单用户即可，多用户权限管理为后续扩展需求
- 现有博客内容（通过 Git 管理的 MDX 文件）需要迁移或兼容到新的后台管理系统
- 媒体文件存储使用本地文件系统，后续可扩展支持云存储（如 AWS S3、阿里云 OSS 等）
- 后台管理系统的前台网站更新机制需要与现有的 Astro 静态构建流程协调——具体方案需在规划阶段确定
